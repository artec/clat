# DSH compatibility evidence matrix

CLAT uses DeepSeek Harness (DSH) as the reference implementation for
interoperable event, session, permission, and plugin surfaces. This document
states only what executable evidence proves at pinned DSH revision
`b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`.

The status vocabulary is deliberately strict:

- **compatible** — a committed fixture was generated by the pinned DSH runtime
  and a CLAT consumer test compares the corresponding behavior;
- **partial** — some behavior exists, but no oracle covers the whole stated
  contact point;
- **intentional-difference** — CLAT deliberately narrows or changes the
  behavior and tests/documentation make the boundary explicit;
- **unresearched** — no current evidence supports a compatibility claim.

A row without a DSH-generated fixture cannot be marked compatible. Source
inspection, package counts, TypeScript compilation, and a successful startup
are useful diagnostics, but they are not compatibility evidence.

## Reproducing the oracles

Oracle generation is a maintainer operation. CI and CLAT users consume only
the committed JSON fixtures and do not need Bun, Node, a DSH checkout, or
credentials.

```bash
DSH_ROOT=../deepseek-harness npm --prefix sdk/dsh-adapter run oracle:regen
npm --prefix sdk/dsh-adapter test
cargo test --all-targets --all-features
```

`oracle:regen` checks the pinned source wiring, runs each generator twice,
requires byte-identical output, and writes generator/checker/fixture SHA-256
values to `tests/fixtures/dsh-oracle/manifest.json`. Generators import only the
pinned upstream checkout; CLAT code is used solely by consumer tests. Fixtures
are registered `text eol=lf` in `.gitattributes` because they are textual
goldens consumed as exact bytes.

## Re-pinning

Re-pin only when at least one of these conditions holds:

1. a real plugin requirement reaches an unimplemented seam;
2. upstream publishes a security or breaking change relevant to a contact
   point above;
3. one quarter has elapsed since the last pin.

A re-pin is an isolated review: regenerate every fixture, rerun the official
cohort, update the revision here, and record every changed section. CLAT does
not continuously chase the DSH main branch, because a moving oracle cannot
serve as compatibility evidence.
